## User Scenarios & Testing *(mandatory)*

### User Story 1 - 네트워크 토폴로지 시각화 (Priority: P1)

운영자는 가상 머신(VM)에서 시작하여 실제 물리 호스트까지의 전체 네트워크 경로를 시각적으로 확인할 수 있습니다. 이를 통해 네트워크 트래픽이 어떤 경로를 통해 흐르는지, 어떤 네트워크 장비와 연결을 거치는지 한눈에 파악할 수 있습니다.

**Why this priority**: 네트워크 토폴로지 시각화는 사용자가 강조한 핵심 기능이며, 네트워크 문제 진단과 성능 최적화에 필수적입니다. 이 기능만으로도 독립적인 가치를 제공할 수 있습니다.

**Independent Test**: 운영자가 특정 VM을 선택하고 해당 VM의 네트워크 토폴로지를 요청하면, VM부터 물리 호스트까지의 모든 네트워크 경로가 시각적으로 표시됩니다. 이를 통해 네트워크 구조를 이해하고 문제를 진단할 수 있습니다.

**Acceptance Scenarios**:

1. **Given** 오픈스택 환경에 여러 VM이 실행 중이고, **When** 운영자가 특정 VM의 네트워크 토폴로지를 조회하면, **Then** VM부터 시작하여 가상 스위치, 물리 네트워크 인터페이스, 호스트까지의 연결 경로가 시각적으로 표시됩니다.

2. **Given** 네트워크 토폴로지가 수집되어 있고, **When** 운영자가 특정 네트워크 경로를 선택하면, **Then** 해당 경로를 구성하는 모든 네트워크 요소(포트, 스위치, 라우터 등)의 상세 정보가 표시됩니다.

3. **Given** 여러 VM이 동일한 물리 호스트에 연결되어 있고, **When** 운영자가 해당 호스트의 네트워크 토폴로지를 조회하면, **Then** 해당 호스트에 연결된 모든 VM과 네트워크 경로가 함께 표시됩니다.

---

### User Story 2 - 오픈스택 리소스 모니터링 (Priority: P2)

운영자는 오픈스택 환경의 주요 리소스(서버, 프로젝트, 네트워크, 하이퍼바이저, 플레이버, 볼륨)에 대한 실시간 상태와 메트릭을 확인할 수 있습니다. 이를 통해 전체 인프라의 건강 상태를 파악하고 문제를 조기에 발견할 수 있습니다.

**Why this priority**: 전체 리소스 모니터링은 시스템 운영의 기초가 되며, 네트워크 토폴로지와 함께 사용하면 더욱 효과적입니다. 하지만 네트워크 토폴로지 없이도 독립적으로 가치를 제공할 수 있습니다.

**Independent Test**: 운영자가 모니터링 대시보드를 열면, 모든 오픈스택 리소스의 현재 상태, 사용률, 성능 메트릭이 실시간으로 표시됩니다. 이를 통해 시스템 전반의 상태를 한눈에 파악할 수 있습니다.

**Acceptance Scenarios**:

1. **Given** 오픈스택 환경이 실행 중이고, **When** 운영자가 서버 모니터링 페이지를 조회하면, **Then** 모든 서버 인스턴스의 상태, CPU 사용률, 메모리 사용률, 네트워크 트래픽이 표시됩니다.

2. **Given** 여러 프로젝트가 존재하고, **When** 운영자가 프로젝트별 리소스 사용량을 조회하면, **Then** 각 프로젝트가 사용하는 서버, 네트워크, 볼륨 등의 리소스가 집계되어 표시됩니다.

3. **Given** 하이퍼바이저가 여러 개 있고, **When** 운영자가 하이퍼바이저 모니터링을 조회하면, **Then** 각 하이퍼바이저의 상태, 호스팅 중인 VM 수, 리소스 사용률이 표시됩니다.

4. **Given** 네트워크 리소스가 구성되어 있고, **When** 운영자가 네트워크 모니터링을 조회하면, **Then** 모든 네트워크의 상태, 연결된 VM 수, 트래픽 통계가 표시됩니다.

5. **Given** 플레이버와 볼륨이 존재하고, **When** 운영자가 플레이버 및 볼륨 모니터링을 조회하면, **Then** 각 플레이버의 사용 현황과 각 볼륨의 상태, 용량, 연결 정보가 표시됩니다.

### User Story 3 - 모니터링 데이터 조회 및 분석 (Priority: P3)

운영자는 과거 모니터링 데이터를 조회하고, 시간대별 트렌드를 분석하여 용량 계획이나 성능 최적화를 수행할 수 있습니다. 또한 특정 리소스에 대한 상세 메트릭을 확인하여 문제의 원인을 파악할 수 있습니다.

**Why this priority**: 데이터 조회 및 분석은 장기적인 운영과 최적화에 유용하지만, 실시간 모니터링과 토폴로지 시각화보다는 덜 시급합니다. 독립적으로 구현 가능하며 가치를 제공합니다.

**Independent Test**: 운영자가 특정 리소스의 과거 데이터를 조회하면, 시간대별 메트릭 변화가 그래프로 표시되어 트렌드를 분석할 수 있습니다.

**Acceptance Scenarios**:

1. **Given** 모니터링 데이터가 일정 기간 수집되어 있고, **When** 운영자가 특정 서버의 지난 24시간 CPU 사용률을 조회하면, **Then** 시간대별 CPU 사용률 그래프가 표시되어 피크 시간대를 파악할 수 있습니다.

2. **Given** 네트워크 트래픽 데이터가 수집되어 있고, **When** 운영자가 특정 네트워크의 지난 주 트래픽 통계를 조회하면, **Then** 일별 평균 트래픽과 최대 트래픽이 표시되어 용량 계획에 활용할 수 있습니다.

3. **Given** 여러 리소스의 메트릭이 저장되어 있고, **When** 운영자가 프로젝트별 리소스 사용량을 비교 조회하면, **Then** 각 프로젝트의 리소스 사용량이 비교 차트로 표시되어 불균형을 파악할 수 있습니다.

---

### Edge Cases

- **오픈스택 API가 일시적으로 응답하지 않을 때**: 시스템은 재시도를 시도합니다. 재시도 후에도 일부 리소스만 수집 실패한 경우(부분 실패), 수집 가능한 부분 데이터를 표시합니다. 모든 리소스 수집이 실패한 경우(전체 실패), 명시적인 오류 상태를 표시합니다. 이전 데이터는 표시하지 않습니다.
- **네트워크 토폴로지 수집 중 일부 네트워크 요소에 접근할 수 없을 때**: 시스템은 수집 가능한 부분의 네트워크 경로를 표시하고, 접근할 수 없는 요소는 명시적으로 표시합니다 (예: "알 수 없음" 또는 시각적으로 구분되는 표시). 전체 토폴로지 수집을 실패로 처리하지 않습니다.
- 매우 큰 규모의 오픈스택 환경(수천 개의 VM)에서 토폴로지 시각화 성능은 어떻게 보장되는가?
- **동적으로 생성되고 삭제되는 VM의 네트워크 경로**: 시스템은 다음 수집 주기(1분)에 자동으로 반영합니다. 별도의 실시간 추적은 수행하지 않으며, 정기적인 수집 주기에 따라 VM 생성/삭제 상태와 네트워크 경로가 업데이트됩니다.
- **네트워크 경로에 루프나 복잡한 다중 경로가 있을 때**: 시스템은 모든 가능한 경로를 표시하고, 각 경로를 시각적으로 구분합니다 (예: 다른 색상, 레이어, 또는 선 스타일). 사용자는 모든 경로를 동시에 확인할 수 있습니다.
- **오픈스택 서비스가 중단되었을 때**: 시스템은 사용자에게 오류 상태를 명시적으로 표시하고, 백그라운드에서 주기적으로 재시도를 계속 시도합니다. 서비스가 복구되면 자동으로 정상 수집을 재개합니다.
- **수집된 데이터가 데이터베이스 용량을 초과할 때**: 시스템은 자동으로 오래된 데이터를 삭제합니다 (FIFO 방식). 최소 보관 기간 30일은 유지하며, 그 이후의 오래된 데이터부터 순차적으로 삭제하여 저장 공간을 확보합니다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 오픈스택 API를 통해 서버(인스턴스)의 상태, 리소스 사용률, 메트릭을 주기적으로 수집해야 합니다.

- **FR-002**: 시스템은 오픈스택 프로젝트별 리소스 사용량을 집계하고 표시해야 합니다.

- **FR-003**: 시스템은 네트워크 리소스(네트워크, 서브넷, 포트, 라우터)의 상태와 연결 정보를 수집해야 합니다.

- **FR-004**: 시스템은 하이퍼바이저의 상태, 호스팅 중인 VM 목록, 리소스 사용률을 수집해야 합니다.

- **FR-005**: 시스템은 플레이버(인스턴스 타입)의 사용 현황과 볼륨의 상태, 용량, 연결 정보를 수집해야 합니다.

- **FR-006**: 시스템은 VM부터 시작하여 가상 네트워크, 물리 네트워크 인터페이스, 호스트까지의 전체 네트워크 경로를 추적하고 수집해야 합니다. 동적으로 생성되거나 삭제되는 VM의 경우, 다음 수집 주기(1분)에 자동으로 반영되어야 합니다.

- **FR-007**: 시스템은 수집된 네트워크 토폴로지 정보를 시각적으로 표현하여 사용자가 네트워크 경로를 이해할 수 있게 해야 합니다. 일부 네트워크 요소에 접근할 수 없는 경우, 수집 가능한 부분은 표시하고 접근 불가능한 요소는 명시적으로 표시해야 합니다. 루프나 다중 경로가 있는 경우, 모든 가능한 경로를 표시하고 시각적으로 구분해야 합니다.

- **FR-008**: 시스템은 수집된 모든 모니터링 데이터를 영구 저장소에 저장하여 과거 데이터 조회가 가능해야 합니다.

- **FR-009**: 시스템은 실시간 모니터링 데이터를 대시보드에 표시해야 합니다. 데이터 수집 후 1분 이내에 대시보드에 반영되어야 합니다.

- **FR-010**: 시스템은 사용자가 특정 리소스의 과거 메트릭을 시간 범위를 지정하여 조회할 수 있어야 합니다.

- **FR-011**: 시스템은 네트워크 토폴로지에서 특정 경로나 요소를 선택하면 상세 정보를 표시해야 합니다.

- **FR-012**: 시스템은 모니터링 데이터 수집 실패 시 오류를 기록하고, 가능한 경우 재시도해야 합니다. 오류 처리 전략은 일관되게 적용되어야 합니다: 부분 실패(일부 리소스만 수집 실패)의 경우 수집 가능한 부분 데이터를 표시하고, 전체 실패(모든 리소스 수집 실패)의 경우 명시적인 오류 상태를 표시해야 합니다. 이전 데이터는 표시하지 않습니다. 오픈스택 서비스가 중단된 경우, 오류 상태를 표시하고 백그라운드에서 주기적으로 재시도를 계속하며, 서비스 복구 시 자동으로 정상 수집을 재개해야 합니다.

- **FR-013**: 시스템은 오픈스택 인증 정보를 안전하게 관리하고 사용해야 합니다.

- **FR-016**: 시스템은 단일 운영자 역할만 지원하며, 모든 인증된 사용자는 동일한 권한을 가집니다. 역할 기반 접근 제어나 프로젝트별 권한 제어는 필요하지 않습니다.

- **FR-014**: 시스템은 대규모 오픈스택 환경에서도 성능 저하 없이 동작해야 합니다. 대규모 환경에서의 응답 시간 증가는 20% 이내로 제한되어야 합니다.

- **FR-015**: 시스템은 모니터링 데이터를 최소 1분 간격으로 수집하며, 최소 30일 이상의 데이터를 보관해야 합니다.

- **FR-017**: 시스템은 데이터베이스 용량이 초과될 경우, 최소 보관 기간(30일)을 유지하면서 자동으로 오래된 데이터를 삭제해야 합니다 (FIFO 방식).

### Key Entities *(include if feature involves data)*

- **서버 인스턴스**: 오픈스택에서 실행 중인 가상 머신. 상태, 리소스 사용률, 네트워크 연결 정보를 포함합니다.

- **프로젝트**: 오픈스택 리소스를 그룹화하는 단위. 프로젝트별로 사용하는 리소스(서버, 네트워크, 볼륨)를 집계합니다.

- **네트워크 리소스**: 네트워크, 서브넷, 포트, 라우터 등 네트워크 구성 요소. 연결 관계와 트래픽 정보를 포함합니다.

- **하이퍼바이저**: 물리 호스트에서 VM을 실행하는 시스템. 호스팅 중인 VM 목록과 리소스 사용률을 포함합니다.

- **플레이버**: VM 인스턴스 타입 정의. CPU, 메모리, 디스크 사양을 포함하며, 사용 현황을 추적합니다.

- **볼륨**: 영구 스토리지 볼륨. 상태, 용량, 연결된 인스턴스 정보를 포함합니다.

- **네트워크 토폴로지**: VM부터 물리 호스트까지의 네트워크 경로. 가상 스위치, 물리 네트워크 인터페이스, 호스트 간의 연결 관계를 포함합니다.

- **모니터링 메트릭**: 리소스별 성능 데이터(CPU, 메모리, 네트워크 트래픽 등). 시간대별로 저장되어 트렌드 분석에 사용됩니다.

- Q: 네트워크 토폴로지 수집 중 일부 네트워크 요소 접근 불가 시 처리 방식은? → A: 수집 가능한 부분만 표시하고, 누락된 요소는 명시적으로 표시 (예: "알 수 없음" 또는 시각적 구분 표시)
- Q: 데이터베이스 용량 초과 시 처리 방식은? → A: 자동으로 오래된 데이터 삭제 (FIFO 방식, 최소 보관 기간 30일 유지)
- Q: 네트워크 경로의 루프 및 다중 경로 처리 방식은? → A: 모든 가능한 경로를 표시하고 시각적으로 구분 (다른 색상, 레이어, 또는 선 스타일 사용)
- Q: "실시간 모니터링 데이터"의 업데이트 주기는? → A: 1분 이내 업데이트 (데이터 수집 주기와 동일)
- Q: "성능 저하 없이" 동작의 기준은? → A: 응답 시간 증가 20% 이내 (대규모 환경에서도 허용 가능한 수준)
- Q: 오류 처리 전략 일관성은? → A: 부분 실패는 부분 데이터 표시, 전체 실패는 오류 표시 (현재 토폴로지 방식 적용)
- Q: 동적으로 생성/삭제되는 VM 추적 방식은? → A: 다음 수집 주기(1분)에 자동 반영 (별도 실시간 추적 없음)
- Q: 오픈스택 서비스 중단 시 모니터링 시스템 동작은? → A: 오류 상태 표시 및 백그라운드 재시도 계속 (서비스 복구 시 자동 재개)
